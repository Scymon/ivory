# Ivory Product Principles

These principles guide product and engineering decisions.

## 1. Structure without imprisonment

Ivory provides a structural core, but users must be able to extend that structure for their own life, organization, profession, or domain.

## 2. Knowledge before interface

The underlying information model matters more than any particular screen. UI should reveal and manipulate the knowledge model rather than become the model.

## 3. Local knowledge belongs to the user

User-authored knowledge should remain accessible through ordinary files and documented formats wherever practical.

## 4. Things, not merely notes

A note may represent a person, place, object, concept, project, event, source, or another entity. Ivory should preserve that meaning rather than treating every resource as an undifferentiated document.

## 5. Relationships are first-class

Knowledge is partly defined by how things relate. Relations must be queryable and navigable rather than existing only as visual decoration.

## 6. One core, many domains

Personal knowledge, company knowledge, research, production, legal work, and other domains should extend a common foundation rather than fragment Ivory into unrelated applications.

## 7. Native first, compatibility second

Build the correct Ivory capability first. Adapt that capability to compatibility APIs afterward.

## 8. Compatibility is explicit

Never imply universal plugin compatibility. Support is versioned, tested, and documented.

## 9. Extensibility is foundational

Plugins and modules are part of the architecture, not an afterthought.

## 10. Context should be computable

Ivory should make it possible for software and AI to determine what information is relevant through types, relations, sources, scopes, and context rather than indiscriminately loading entire vaults.
